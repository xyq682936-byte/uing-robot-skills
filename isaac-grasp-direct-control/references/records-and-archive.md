# 记录、总库与归档

创建存档、采集数据及结束或恢复批次时读取本文件。

## 目录与文件

所有存档进入用户指定的根目录。默认建议以下分区，用户可改名称和日期组织方式：

```text
用户指定根目录/
  标准库/
  参考资料/
  用户模型文件复制/
    原始副本/<模型编号>/<导入编号>/
    备份/<模型编号>/<导入编号>/
    转换工作区/<模型编号>/<转换编号>/
    已转换好/<模型编号>/<转换版本>/
  成功库/成功策略总表.csv
  成功库/优化结果/<物体编号>/<父策略编号>/<优化任务编号>/
  失败库/失败策略总表.csv
  YYYY-MM-DD/
    HHmmss-唯一批次或会话编号/
      本轮配置.json
      预算与恢复状态.json
      YYYYMMDD-HHmmss-唯一编号-策略方案表.csv
      结论.md
      原始数据/
      trace/events.jsonl
      trace/index.json
      证据索引.json
```

总体目录是组织建议，不要求覆盖现有可用结构。用户模型接入时需按 [模型副本规则](asset-intake-and-conversion.md) 在用户指定库内设置“用户模型文件复制”及其直接子目录“已转换好”；保留原件、原始副本与独立备份，实际转换只修改工作副本。每个模型版本关联来源、依赖、评估、授权、转换与验证记录。

默认 UTF-8 CSV；用户已有其他表格格式时保持兼容。“三张表”指两张长期总表和一张本次合并表，不要求把原始轨迹或运行日志塞进表格，也不限制保存必要的原始数据文件。

当日目录已存在就复用，不覆盖旧会话。同一天多次运行用具体时间和唯一编号区分。跨日恢复保留原批次编号及预算，在新会话目录中关联上次检查点；项目级两张总表持续沿用。

成功总库、失败总库分别只维护一张当前业务总表；不得每轮再生成一张“新的总表”。备份或版本历史如需保留，应明确为备份，不作为新的统计来源。

## 编号与表字段

同一套编号贯穿三张表、原始数据与配置：

- `object_id`：稳定物品身份，另记资产版本；
- 机械臂实例编号与设备身份分开：每条试次关联机械臂和夹爪的品牌、型号、仿真模型版本、资产哈希及实际参数快照；允许引用同一冻结配置，但不能只记录 arm_id。缺失项标待补全，不从臂序号猜型号，也不因更换设备继承旧成功结论；
- `strategy_id`：独立策略身份；
- `revision_id`：微调分支或修订；
- `batch_id` / `session_id`：批次及本次实际运行；
- `trial_id`：真实执行试次；
- `protocol_id` / `environment_id`：有效标准配置与环境版本。
- `trace_id` / `event_id`：会话追踪与事件定位；`action_id` 将短动作的准备、发送、确认和结果关联起来。具体语义见 [Trace 执行追踪规则](trace-and-replay.md)。

总表按物品、策略和适用标准配置关联汇总，保存修订、环境和证据索引；不同标准的结果分开标记，不能继承“通过”标签。

三张表至少能够查到：物品与策略编号、策略描述、物体坐标系下的抓取区域及接近方向、独立或微调关系、试次和各阶段结果、实际试次及失败次数、验证次数、复核状态、标准状态、失败原因、剩余工作、适用版本、原始证据路径及 trace 入口。批次表还包含本次分配和机会结算结果。历史数据没有 trace 时标记缺失；仅根据旧日志建立的索引标记为事后关联，不冒充现场采集。

候选表记录部位、接触关系（双指夹爪记录两指对应关系）、进入通道及计划覆盖，运行结果只记录实际发生的接触和路径。未探索、待核实、有依据待实跑、已尝试和有证据排除分别记录，排除关联具体几何/物理证据及适用组合，不外推为整个部位不可行；不能仅凭候选状态计为已完成策略。

总表中同策略不同适用条件可以有分开的结果记录，但全局“独立策略数”按稳定策略身份去重，不能因标准版本或复测次数变多就增加方案数。

## 三张表的更新规则

1. 《成功策略总表》：追加或更新本次实际成功方案；明确是探索成功、重复验证成功还是完成指定标准验收。重复成功增加试次或验证统计，不增加新方案。
2. 《失败策略总表》：追加或更新本次实际失败或开始执行后淘汰的方案，保存原因及证据。后来微调成功也保留原失败历史，并关联成功记录。
3. 《时间-策略方案表》：只收录本次实际开始执行的方案，标注成功、失败、混合结果或技术中断及机会状态。未执行候选保留在本轮配置或策略队列中，不伪装成本次试验结果。

一个策略先失败后成功，可以同时存在于成功总表和失败总表；同次合并表关联全部试次并标为混合结果。两张总表行数相加不等于独立方案数。单纯启动异常和接口异常记技术故障，不把无抓取证据的方案放入抓取失败统计。

物品编号、策略编号、试次编号及适用版本共同支持去重。重复执行归档、恢复任务或重复导入同一数据，不能重复累计成功、失败或验证次数。更新失败时保留原表和待合并记录，修复后续写，不能从头清空总库。

## 优化结果模式的独立文件夹与完成记录

在原库“成功库/优化结果”独立文件夹保存源成功证据清单、所有相关成功臂数据索引、原版与优化版、基线复现、新试次/复核、分项时间、失败或无改进及状态。按 [完成去重规则](success-replay-and-acceleration.md#空闲批量优化与完成去重) 为父策略、源及产出版本建立同一可恢复优化任务记录，区分未复训、排队、复训中、暂停、完成有优化、完成无改进、失败/缺证据及适用性待复核。完成状态关联原三表/模型登记，作为统一账本，不额外建立第二套事实库；重复导入、重启或换 agent 不再复训已完成项。失败或中断不假标完成，有限恢复沿用原任务。

保存各自真实轨迹，不拼接不同臂或不同试次冒充一次成功；无新复核的优化候选不得作为已验证记忆入口。操作经验按任务、前后条件、接触、反馈和依赖关系关联证据，供后续检索及组合验证。

## 批后成功策略优化的归档

整批筛选完成后才按 [成功策略单独优化](success-replay-and-acceleration.md) 提炼实测参考并单独复跑；筛选期间只按原安排记录和复核，不穿插提速优化。关联源批次完成状态、已复核成功集合、父策略、提炼方法及源证据、优化修订、新试次与独立复核，保存有效配置/资产哈希及前后分阶段耗时，区分调度收益、动作时序变化与动作范围变化。更新原三张表和已有库，不再建立另一套成绩库。区分最新编辑版本与最新验证通过版本，保留旧成功及失败记录；没有新实跑复核的优化版本不能替换已验证入口，也不继承完整标准通过标签。

## 实际场景与碰撞修正的结果范围

按 [实际场景模式](actual-scene-mode.md) 在原库记录源策略、场景/任务差异、用户调用、失败阶段、针对性探索分支与原失败场景复核。保留原成功范围和优化完成标记；新场景成功不等于所有场景通过，多步任务分别报告阶段结果与整体结果。针对性探索不算重复复训，同一策略跨场景验证不虚增独立策略数。

按 [碰撞内存修正](asset-intake-and-conversion.md#碰撞体误堵空隙的内存修正与询问) 用原碰撞版本和临时修正版本分别统计试次、失败、成功、标准结果及分母；保留授权和参数核对。总体汇总须展示分组，不能将两组混成同条件成功率或宣称原模型通过；修复验证与探索抓取分列，预算与真实失败仍累计。仅内存修正保存证据和可复现说明，不持久改写资产，不冒充已完成持久转换。

## 原始证据与恢复

执行时保存带仿真时间戳的控制指令、物体与夹爪状态、关节状态、可用接触反馈、试次和复位事件，以及验收所需的其他测量。不可用的量标记缺失，不能用推测值冒充传感器记录。

保存控制与环境配置、资产版本、随机种子（如使用）、关键实现版本和证据索引，保证成功方案可在相同条件下重放或复验。视觉证据用于辅助核对，不能替代所需物理测量；回放和新发生的试验分开标注。

每次策略派发、结果确认及暂停时保存预算检查点。将用户确认的 X、臂—物体—策略分配、待续接/补位事项、控制与监管实例、有效规则/配置版本、最后有效反馈和监管检查、过期/恢复状态共同关联持久化；优先扩展既有状态记录，不新建另一套业务库。启动、跨天或上下文/程序恢复时，按 [持续监管规则](parallel-runtime-and-demo.md#每批启动与持续监管) 与最新现场核对后接续，保留失联缺口，不重置数量、预算或失败，不重复启动。原始事件应保留可追溯记录；汇总表可由这些记录重建。多个写入者不得无保护地同时改总表，采用单一归档者、互斥或等效方式，避免覆盖。

归档采用临时文件写完后替换或环境已有的可靠机制，避免半写入数据成为有效总表。核对三表关联、计数、文件可读性和证据路径；大文件可用大小与校验信息核对，不要求复制所有历史原始资产。

## 报告必须区分的数量

向用户展示以下结果状态，并注明物品、策略、试次及复核范围。运行活动状态另行记录，不能用“机械臂已停止”推断验证完成。

| 用户可见状态 | 使用条件 |
|---|---|
| 已执行，待复核 | 动作结束，但相关测量核对或验证尚未完成；不能据此报告通过 |
| 验证完成—成功 | 指定范围的证据已核实，满足该范围的判据；注明是探索、复测还是标准验收 |
| 验证完成—失败 | 证据已核实且不满足判据；失败同样是明确结果，记录原因 |
| 未完成—中断／缺证据 | 执行或复核未完成，说明缺口、影响范围及下一步；未知不算成功或抓取失败 |
| 整批验证完成 | 全部适用测试、复核和归档完成，包含明确的成功与失败结果；不等于所有策略成功 |

整批仍有未执行、未复核或缺少必要证据的适用项目时，不能标记“整批验证完成”。批次关闭、程序退出、预算耗尽和整批验证完成分别表达。

采用成功目标停止时，逐物品报告目标 K、计数范围、已复核独立成功数、机会消耗/未使用数及停止原因。达到目标后按已确认规则取消、尚未启动的剩余探索候选标记“未执行—目标达成后取消”，不算成功或失败，也不因为未用完预算而一概判整批未完成。已实际开始的试次仍须保留收尾结果和必要验证；取消不能豁免已经发生的测试所需证据。全部物品均按确认的停止规则收尾，且适用验证、复核与归档完成后，才可报告整批验证完成。额度耗尽但不足 K 时同时明确“成功目标未达成”。

- 本次与累计独立成功策略数；
- 探索机会已确认、预留、已消耗、已完成、暂停和剩余数；
- 实际抓取试次数、实际失败次数、提前淘汰数及其中实际失败为零的数量、技术故障数；等待、接近超时与重规划单独列事件及持续时间，不与试次次数相加；
- 额外验证的已约定、已完成及剩余次数；
- 探索成功、复测达标、指定标准通过、未测试和证据不完整的数量。

队列状态和失败总表行数不能代替实际失败计数；按 [动作中断与失败分类](strategy-and-budget.md#动作中断与抓取失败分类) 核对同一试次的事件关系，保留已发生的空夹、掉落和其他真实失败。

所有成功率都注明统计单位、分母和条件。不得只用精选成功片段计算整体成功率；不同物品、标准或环境混合统计时要能追溯分组。没有开展神经网络训练时明确记录“未进行神经网络参数训练”，不能把数据量描述成模型学习进度。

## 可选回传与本地归档的关系

启用成功数据回传时遵循 [成功数据回传规则](success-data-upload.md)。仅对用户本次选定且已授权回传的成功试次关联导出清单、记录修订、数据包哈希和上传队列状态；核对这一授权集合与打包结果，报告其中未导出或打包失败项。未选中/未授权的试次保留本地，不视作漏传并自动补发；贡献分享单独关联授权记录，不混入成功试次包。相同试次重复打包或重试不增加抓取次数和独立策略数。

本地归档、成功复核、标准状态和接收端确认分别记录。接收服务未配置、上传排队或失败不撤销已有本地成功结论，但不能报告后台已收到。没有完成必要物理证据复核的试次不得借上传流程进入成功库。上传后保留本地原件，接收凭据和用户授权记录与可分发技能包分开保存。

## 用户贡献与库的连续性

用户补充规则和物体策略时，按 [贡献评估与归档规则](user-contributions-and-review.md) 在现有存档根目录保留原文、整理/优化版本、适用范围、来源、等级/待评状态、评估依据和证据关联。贡献记录与实际成功、失败试次分开；未实跑的建议不进入本次实际执行方案表，也不增加成功数量。原文、修订与三张表通过稳定身份关联，不再复制一套训练总表。

更新技能、程序或评级方案，沿用已配置的存档位置、库标识和历史记录。换日期、新物体、新批次只增加分组或记录；备份不作为第二套正式库。首次确认不存在已有库时才初始化，旧库不可用先报告恢复/迁移问题；不得静默创建空库冒充原库。必要迁移备份后增量执行，保留稳定编号、关系、原始证据、预算和恢复状态，并核对前后数量/哈希；没有迁移实现时明确待适配。重复更新或重传不得重复新增同一记录，冲突保留诊断；不同真实试次仍独立保存。详见 [更新复用原库](user-contributions-and-review.md#更新复用原库)。
